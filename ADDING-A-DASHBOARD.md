# Adding a Dashboard

Drop a `.json` file into `monitoring-stack/dashboards/`, run `make upgrade`, done.
No template edit, no `values.yaml` edit, no manual import in the Grafana UI.

```bash
cp my-dashboard.json monitoring-stack/dashboards/
make upgrade
```

The rest of this document explains what that does, the one step people skip that
produces a dashboard full of empty panels, and the conventions a new dashboard
should follow so it looks like the four that already ship.

---

## How provisioning works

There is no import step and nothing is downloaded at runtime. The chain is:

```
dashboards/*.json
      │
      │  templates/grafana-dashboards.yaml  —  .Files.Glob, one ConfigMap per file
      ▼
ConfigMap  monitoring-dashboard-<slug>      labelled  grafana_dashboard: "1"
      │
      │  k8s-sidecar container in the Grafana pod, watching that label
      ▼
/tmp/dashboards/<file>.json  inside the Grafana pod
      │
      │  Grafana's file provisioner
      ▼
Dashboard, live, no restart
```

Three consequences worth knowing:

- **The file name becomes the ConfigMap name.** `keycloak.json` becomes
  `monitoring-dashboard-keycloak`. Keep names lowercase and hyphenated.
- **The sidecar watches its own namespace only.** `sidecar.dashboards.searchNamespace`
  is deliberately unset in `values.yaml` — see the comment there, it expects a list
  and the usual `ALL` string fails to render. Dashboard ConfigMaps must live in
  `monitoring`.
- **Pickup takes about 30 seconds.** No pod restart, no `helm rollback` needed.

## Step 1 — Get the JSON

Three ways, in descending order of how well they end up working:

**Write it by hand (or generate it).** Most reliable, because you control every
query. `dashboards/keycloak.json` was generated by a short Python script — that
is a good pattern for anything with more than about ten panels, since it keeps
panel geometry consistent and makes bulk edits trivial.

**Draft in the Grafana UI, then export.** Build it live at
`http://192.168.56.134:30300`, then **Dashboard settings → JSON Model**, and copy
the JSON into a file. Do not use *Share → Export → "Export for sharing
externally"* — that rewrites datasources into `${DS_...}` input variables which
this chart does not provide, and the dashboard will fail to load.

**Import from grafana.com.** Paste the JSON, then fix the datasource references
by hand (see Step 2). Community dashboards usually assume a datasource named
`Prometheus` and a stock `kube-prometheus-stack`, so expect to rewrite queries.

## Step 2 — Bind it to this stack

### Datasource UIDs are fixed

Every panel and every template variable must reference one of these. They are
provisioned statically in `values.yaml` and never change:

| UID | Type | Use it for |
|---|---|---|
| `victoriametrics` | prometheus | **Default.** All metrics. 15-day retention. |
| `prometheus` | prometheus | Only when you specifically want the 6h scraper view |
| `loki` | loki | All logs |
| `alertmanager` | alertmanager | Alert state |

```json
"datasource": { "type": "prometheus", "uid": "victoriametrics" }
```

Set it on the panel **and** on each target. A panel with a missing or wrong
`uid` renders as "Datasource not found" rather than an error you can miss.

### Required top-level fields

```json
{
  "uid": "keycloak",
  "title": "Keycloak",
  "tags": ["monitoring-stack", "keycloak"],
  "schemaVersion": 39,
  "timezone": "browser",
  "editable": true,
  "refresh": "30s",
  "time": { "from": "now-6h", "to": "now" }
}
```

`uid` must be unique across the whole Grafana instance and is what URLs and the
`make test` checks key off. Always include `monitoring-stack` in `tags` so the
dashboard is filterable alongside the built-in four.

## Step 3 — Validate the queries BEFORE deploying

This is the step that matters. A dashboard whose panels are all empty looks
identical to a working one until someone opens it, and `helm lint` will not
catch a single bad query.

Port-forward the datasources and run every query you are about to ship:

```bash
kubectl port-forward -n monitoring svc/monitoring-victoriametrics-server 8428:8428 &
kubectl port-forward -n monitoring svc/monitoring-loki 3100:3100 &

# a metrics query
curl -s -G http://127.0.0.1:8428/api/v1/query \
  --data-urlencode 'query=sum by (status) (rate(http_server_requests_seconds_count[5m]))' \
  | python3 -m json.tool | head

# a log query
curl -s -G http://127.0.0.1:3100/loki/api/v1/query \
  --data-urlencode 'query=sum by (level) (count_over_time({namespace="monitoring"}[5m]))'
```

To check the whole file at once, extract every target and run it. Substitute the
dashboard variables first — `$__range` and `$__interval` are Grafana-side and
mean nothing to the datasource:

```python
def sub(expr):
    return (expr.replace("$namespace", "monitoring")
                .replace('pod=~"$pod"', 'pod=~".*"')
                .replace('|= "$search"', "")
                .replace("$__range", "30m")
                .replace("$__interval", "5m"))
```

Every query should come back with at least one series. Zero series means either
the metric does not exist, a label name is wrong, or the thing you are measuring
has not happened yet — and you want to know which **before** it ships.

> The Keycloak dashboard was validated this way: 31 panel queries, 31 returning
> data, before the first `make upgrade`.

### Confirm the metric names against the real target

Do not trust a metric name from documentation or memory. Ask the exporter:

```bash
kubectl port-forward -n <ns> svc/<service> 9000:9000 &
curl -s http://127.0.0.1:9000/metrics | grep "^# TYPE"
```

Metric names drift between versions, and counters exposed through Micrometer or
the Prometheus Java client may or may not carry a `_total` suffix depending on
the exporter version. Checking takes ten seconds and removes the guess.

## Step 4 — Deploy

**Validate the JSON yourself first.** Nothing in the Helm pipeline will do it
for you — see the gotcha below:

```bash
python3 -m json.tool monitoring-stack/dashboards/<name>.json > /dev/null && echo "JSON ok"
```

Then deploy:

```bash
helm lint monitoring-stack --set skipReleaseNameCheck=true
make upgrade
```

`make upgrade` is fast for a dashboard-only change — it adds a ConfigMap and
restarts nothing. Roughly four seconds.

---

## Step 5 — Verify it actually loaded

```bash
# the ConfigMap exists and is labelled
kubectl get cm -n monitoring -l grafana_dashboard=1

# Grafana has it (wait ~30s for the sidecar)
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80 &
curl -s -u admin:admin http://127.0.0.1:3000/api/search?type=dash-db \
  | python3 -c "import json,sys; [print(d['uid'], d['title']) for d in json.load(sys.stdin)]"
```

And prove a panel returns data *through Grafana*, which exercises the datasource
binding rather than just the datasource:

```bash
curl -s -u admin:admin -G \
  "http://127.0.0.1:3000/api/datasources/proxy/uid/victoriametrics/api/v1/query" \
  --data-urlencode 'query=up'
```

Finally, `make test` should still report **35 passed, 0 failed**. It does not
check your new dashboard, but it proves you did not break the four that exist.

## House conventions

Match these and the new dashboard will not look out of place.

**Layout.** 24-column grid. Group panels under `row` panels. Stat tiles `h: 5`,
timeseries `h: 8`, log panels `h: 12`–`20`. Full width is `w: 24`, half is `12`,
thirds are `8`.

**Timeseries panels:**

```json
"custom": {
  "drawStyle": "line", "lineWidth": 2, "fillOpacity": 10,
  "showPoints": "never", "spanNulls": true
}
```

with `legend.placement: "bottom"` and `calcs: ["mean", "max"]`.

**Colour.** Use Grafana's default series palette — do not hand-assign colours to
series. Reserve red/orange/green for actual state (up/down, thresholds, error
counts), never as a way to tell two ordinary series apart.

**One axis per panel.** If two measures have different scales, use two panels.

**Write a `description` on every panel.** They surface as the little `i` tooltip
and are the difference between a dashboard someone can act on and one they have
to reverse-engineer. Say what the panel means, not what the query does.

**Units.** Set `fieldConfig.defaults.unit` — `bytes`, `percent`, `s`, `reqps`,
`ops`. An unlabelled axis of raw numbers is a bug.

## Gotchas

**UI edits do not persist.** `sidecar.dashboards.provider.allowUiUpdates` is
`true`, so Grafana lets you save — but the ConfigMap is the source of truth, and
the next `make upgrade` or Grafana restart overwrites whatever you saved. Use
the UI to draft, then export the JSON back into `dashboards/` and commit it.
Never treat the running dashboard as the master copy.

**Metrics and logs answer different questions.** High-cardinality fields —
source IP, username, session id — are usually left out of metric labels on
purpose, because each distinct value is a new time series. They exist only in
the log line. The Keycloak dashboard splits along exactly this seam: rates and
totals from `keycloak_user_events_total`, per-IP and per-username analysis from
Loki. Reach for logs when you need identity, metrics when you need volume.

**Retention differs.** Metrics live 15 days in VictoriaMetrics, logs 7 days in
Loki. A log-derived panel on a 30-day time range is empty for the first three
weeks of it, and that is not a bug.

**Loki queries need a stream selector.** `{namespace="x"}` at minimum — Loki
cannot scan everything. Use `$__interval` for `count_over_time` in timeseries
panels and `$__range` for totals in stat panels.

**Helm replaces lists, it never merges them.** Only relevant if you edit
`values.yaml` rather than adding a file — but if you add a fifth datasource you
must restate all four existing ones or they disappear. `values.yaml` carries the
same warning at the `scrapeConfigs` block.

**Nothing in the Helm pipeline validates your JSON.** The template embeds the
file with `.Files.Get` as an opaque string, so a syntactically broken dashboard
passes `helm lint`, passes `helm template`, and passes `kubectl apply
--dry-run=server` — all three report success. Verified by deliberately shipping
a malformed file:

```
$ helm lint monitoring-stack --set skipReleaseNameCheck=true
1 chart(s) linted, 0 chart(s) failed          # broken file present

$ helm template ... | kubectl apply --dry-run=server -f -
                                              # also passes
```

The ConfigMap is created happily and the failure surfaces only later, inside
Grafana, as a dashboard that never appears. Run `python3 -m json.tool` (or `jq
.`) over the file before every upgrade — it is the only check there is.

## Removing a dashboard

```bash
rm monitoring-stack/dashboards/<name>.json
make upgrade
```

Helm deletes the ConfigMap, the sidecar removes the file, and Grafana drops the
dashboard. Nothing is left behind.

## Worked example

`dashboards/keycloak.json` is the reference. It covers both datasource types,
uses template variables, and mixes metrics, tables and log panels:

- 31 panels across six rows
- `namespace` and `search` textbox variables, `pod` as a query variable driven by
  `label_values(up{namespace="$namespace"}, pod)`
- Metrics rows against `victoriametrics`, audit rows against `loki`
- Every query verified against the live cluster before it was committed

Read it alongside this document when building the next one.
